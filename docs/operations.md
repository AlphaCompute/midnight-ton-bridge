# Deployment, committee operations and liquidity

## Ownership boundaries

The code does not operate itself. A running bridge needs two chain endpoints, a Midnight indexer and proof service, relayer gas/DUST, signers, reconciliation, monitoring and incident response. The POC does not imply that AlphaTON accepts indefinite hosting or funds real liquidity. Assign those roles and costs in writing before public deployment.

The standard Midnight deployment API creates a maintenance authority. This implementation saves its key to `.state/midnight-maintenance-key.json` before deployment. That key can authorize changes to Midnight verifier rules: protect it separately from the committee keys, transfer it securely to the accepted operator, or disable maintenance in a separately verified authority transaction. Do not describe this deployment as immutable. Reverse observers pin both the maintenance authority and the verifier set and stop when either changes. Historical malicious maintenance remains a trust risk; a current pin is not proof of the whole contract history.

Three independent organizations or processes should each hold one committee key pair and query their own trusted chain infrastructure. `npm run operator -- keygen DIRECTORY` generates one Ed25519 TON key and one Jubjub Midnight scalar, with a public-only companion file. The local demo centrally holds three keys solely to test a quorum; that is not decentralized operations.

## Test deployment

1. Build from the delivered lockfile; generate and verify all five prover/verifier key pairs. Review the source/code hashes and dependency/toolchain versions. Preserve the generated verifier fingerprints.
2. For local Midnight, start the Compose services and use the documented public genesis wallet. For preprod, supply a separately funded test wallet seed, MIDNIGHT_COMMITTEE_FILE containing three independently held public keys as decimal-string {x,y} objects, and verify compatible services. Centrally generated demo committee secrets are permitted only on the isolated local network. A functioning local proof server is required. Never log seeds or export `.state`.
3. Run `npm run deploy:midnight` once. Its intent, signed transaction journal, maintenance key and confirmed record are separate evidence. If it fails, inspect the exact journal entry before another attempt. The confirmed deployment record includes the route domain and verifier/maintenance pins.
4. Generate three TON public committee keys. Set `TON_COMMITTEE_FILE` to a JSON array of their hex public keys and `BRIDGE_DOMAIN` to the Midnight deployment's domain. Run `npm run deploy:ton` to create the testnet address plan. It does not submit by default.
5. Fund the generated wallet with faucet test TON. `npm run deploy:ton -- --send` saves the signed deployment body and submits four deployments to the fixed testnet RPC. Verify each account is active with the planned code/config hashes; submission is not acceptance. The minters are deliberately limited fixtures, with separate master addresses.
6. Keep each escrow cap equal to the corresponding Midnight circulating cap (default 1,000,000,000,000 base units). A cap-exceeding direct deposit is unregistered and needs verified surplus recovery; query remaining capacity before sending. Mint fixture tokens to a test user's derived jetton wallets using `npm run mint:ton -- 0 BASE_UNITS RECIPIENT` (or asset 1), which prepares the owner-only minter message exercised in `tests/ton.test.ts`. Send it from the original deployment wallet. Publish the exact test master addresses and base-unit convention, never an official USD1 symbol without a test label. No automatic faucet or issuer integration is included.
7. Assemble a bridge config from the two TON escrows and Midnight record. Fund relayer TON and Midnight DUST independently of LP reserves. Operate and verify the following flow before inviting testers.

## Deposit and return flow

For TON→Midnight, the user sends a TEP-74-style transfer to their verified jetton wallet, with the escrow as destination, 32-byte Midnight recipient as forward payload and sufficient forwarded TON. The escrow authenticates its wallet and records the sequential receipt. A missing receipt is not a valid deposit authorization.

Each committee member runs `npm run operator -- attest-deposit CONFIG SEQUENCE`. The config contains `rpc`, `source: {escrow, asset, codeHash, configHash, confirmationDepth}`, `bridge` as documented in the README, `signer` (0–2), and the private `keyFile`. The observer reads one older masterchain snapshot; its depth is a configured acceptance policy, not a mathematical finality proof. Compare two independently obtained identical receipts; combine their distinct signatures with `BridgeClient.claim`. Never sign a user-supplied receipt without independent observation. A permissive mint circuit would destroy backing; do not introduce one for convenience.

For Midnight→TON, the user calls `redeem` with a random unique 32-byte ID, asset, amount and basechain recipient. It receives real unshielded tokens and permanently locks the retired quantity. Save the finalized transaction ID and full request before proceeding.

Each committee member runs `npm run operator -- attest-redemption CONFIG REQUEST_JSON`. Config contains `network`, `indexer`, `indexerWS`, `address` (Midnight contract), `pins` from the accepted deployment, two `escrows`, `signer`, and private `keyFile`. The request contains `id`, `asset`, decimal `amount`, `recipient` and `transactionId`. The signer waits for a successful finalized transaction, queries that block, checks the accepted verifier set/domain/maintenance authority and matches the retired commitment before signing the TON release digest. Fetching through a trusted indexer is not a light-client proof.

For repeatable transport, use `npm run relay -- claim BRIDGE_CONFIG DEPOSIT_ATTESTATION_A DEPOSIT_ATTESTATION_B` after loading the matching Midnight network environment. Both attestations must agree on canonical transfer fields; independently observed block heights may differ. The claim path validates signatures and waits for successful Midnight finalization.

`npm run relay -- release TON_CONFIG REVERSE_ATTESTATION_A REVERSE_ATTESTATION_B` validates both signatures and prints an unsigned wallet message for review. TON_CONFIG contains `network: "ton-testnet"`, `domain`, two `escrows`, three public-key hex `committee` entries and `walletKeyFile` with a test-wallet seed. Add `--send` to sign and submit through that separately funded wallet; the exact signed body is journaled first, and repeated attempts stop for reconciliation.

Alternatively, combine signatures in signer-index order using `releaseBody` and send at least 0.15 TON to the correct escrow (the SDK wrapper defaults to 0.2). Verify the recipient's authenticated jetton-wallet transaction trace and balance change. `releaseState(id) == 1` means a wallet request was submitted, not that the recipient received tokens. The repository exposes signing and transaction primitives; hosted event ingestion, automatic public-network relaying and a production alert service require an assigned operator and integration validation.

## Liquidity

Escrow collateral and AMM liquidity are different. Depositing 1,000 WHIS locks 1,000 WHIS on TON and allows minting exactly 1,000 units of its Midnight representation. This backing is required for every minted token; it is not an LP subsidy. A lock/mint bridge does not need a second prefunded payout pool on TON because redemption releases its own backing.

For the contractual test pool, use faucet TON and owner-minted synthetic WHIS/test-USD1. Bridge both assets into a test wallet, generate and back up an LP secret, then call `addLiquidity(ownerHash, x, y, minShares)`. The first LP chooses the unit ratio; choose and document decimals and a demonstration price first. Initial shares equal x. Later deposits mint floor(x × totalShares / reserveWHIS) shares and must include at least the corresponding test-USD1 ratio; excess is donated. Swaps retain a 30-bps fee for LPs. Obtain current reserves immediately before quoting and set meaningful minima.

Withdraw through `removeLiquidity(secret, shares, minX, minY, recipient)`; then retire the returned representations to recover TON collateral. LP shares are secret-controlled contract entries, not transferable tokens. LPs bear price/inventory risk. No real dollar peg, market making, guaranteed depth, incentive budget or AlphaTON-funded principal is implemented or promised. Any real liquidity program needs a separately specified asset issuer, legal authority, budget, custody, loss allocation and operator.

## Reconciliation and recovery

The SQLite journal uses WAL, FULL synchronization and compare-and-set transitions. A signed transaction is saved before send. `sending` is ambiguous after a timeout or crash; never create another transaction to replace it blindly. `npm run reconcile -- TRANSACTION_ID` waits for exact Midnight finalization and updates the journal. Unknown/pending remains unresolved; a timeout is not rejection. Failed-fallible transactions are failures, not successful bridge credits. Maintain backups on the same persistence guarantees as the database.

Deployment intents block automatic repeats. When there is no signed submission entry and evidence shows failure before submission, an operator may archive the intent and retry. If an entry exists, reconcile it first and reconstruct the deployment record from finalized evidence. Never delete the journal to get past a retry guard. TON deployment attempts similarly need exact wallet sequence, transaction and destination-account reconciliation.

An immediate bounce from the escrow's own jetton wallet restores normal release accounting and clears that authorization for retry. Later recipient-wallet failure can return tokens without that bounce; independently examine the entire trace. Malformed or unnotified deposits can also leave surplus in the escrow wallet. Recovery opcode `0x42524702` requires two signatures over a separate domain and a unique case ID, moves only the authorized amount, and does not reduce registered backing. The SDK `releaseDigest`/`releaseBody` accept `recovery=true`. This is a trusted committee recovery path; there is no automatic surplus oracle on chain. Confirm returned/unregistered funds from their exact traces and reconcile pending deposits first. Wallet balance minus `locked` is insufficient evidence while messages are in flight. Never sign recovery against live collateral or refund a deposit whose claim remains possible. Archive the evidence, original payer, beneficiary and two approvals.

Monitoring must compare per-asset TON `locked` against Midnight circulating supply plus pending claims/retirements/releases, track pending message ages, source endpoints, signer availability, gas/DUST, LP reserves and code/maintenance changes. Pause signer issuance on mismatch. There is no blanket contract pause or key rotation switch; replacing the committee requires a planned redeployment and backed migration. The code supplies bounded caps and replay guards, not an assurance that compromised quorum or maintenance keys cannot steal funds.
